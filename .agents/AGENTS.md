# Project & NativePHP Rules

## NativePHP Mobile & Android Rules

### 1. Production Build & Vite Asset Safety

- Before every production NativePHP package, run `npm run build`.
- Production packages MUST use the compiled Vite assets from `public/build`.
- NEVER include `public/hot` in a production NativePHP package.
- Before packaging, verify that `public/hot` does not exist. If it exists, remove it before packaging.
- NEVER allow Laravel's `@vite` directive in a production package to reference the Vite development server (`127.0.0.1:5173`).
- Do not delete `public/build` during normal development or packaging unless it is being intentionally regenerated by `npm run build`.
- Do not unnecessarily rebuild frontend assets when no frontend-related files have changed during rapid development iterations.

### 2. NativePHP Packaging & Build Performance

- Preserve reusable build caches and generated Android project files whenever possible.
- NEVER use `--rebuild` unless a rebuild is actually required or the user explicitly requests one.
- When only Laravel/PHP/frontend application code has changed and Android/native configuration has NOT changed, prefer `php artisan native:package android --skip-prepare`.
- Use the normal packaging command without `--skip-prepare` when Android/native configuration has changed.
- Android/native configuration changes include:
  - `config/nativephp.php`
  - Android permissions
  - Android plugins
  - Gradle configuration
  - Native Android source code
  - Application ID/package configuration
  - App name/icon configuration
  - NativePHP configuration that affects the Android project
- NEVER delete Composer, npm, Gradle, or other build caches merely to make a build "clean."
- Only clear caches when necessary to resolve a verified build/cache problem.
- Do not delete `vendor/` before packaging unless dependency corruption or an intentional dependency reinstall requires it.
- Do not repeatedly reinstall dependencies when the existing dependency installation is valid.
- Do not perform unnecessary clean/rebuild operations during normal release iteration.

### 3. Composer Dependencies in Production Packages

- Production NativePHP packages MUST use the project's `composer.lock`.
- Composer dependencies MUST be installed deterministically from `composer.lock`.
- Production packaging should use production dependencies where appropriate with `composer install --no-dev --optimize-autoloader`.
- Do not modify or delete `composer.lock` merely to resolve a packaging problem.
- Do not delete `vendor/` as a workaround for build problems.
- If Composer installation fails, diagnose and fix the dependency problem rather than deleting unrelated project data or databases.

### 4. PHP 8 Exception Handling

- In Laravel controllers, NativePHP WebView APIs, Inertia endpoints, and other application endpoints, catch `\Throwable` rather than only `\Exception` when handling unexpected runtime failures.
- PHP `\TypeError` and `\Error` are `\Throwable` but are not `\Exception`.
- Do not hide programming errors with overly broad exception handling.
- Log unexpected failures appropriately and return a safe user-facing response.

### 5. Safe JavaScript Bridge Injection

- NativePHP Android WebView JavaScript bridge/injection code MUST verify overridden native functions exist before invoking them.
- When wrapping XMLHttpRequest methods, always perform checks such as `typeof originalXHRSend === 'function'`.
- Never assume browser/WebView APIs or previously overridden prototypes exist.
- Bridge/injection failures MUST NOT create uncaught promise rejections or crash the WebView.
- Preserve the original browser behavior when the native bridge is unavailable.

### 6. Release Versioning & In-Place Android Upgrades

- Every Android release MUST have a higher `version_code` than the previous release.
- `version_code` MUST be an integer and MUST monotonically increase.
- `version` MUST be a valid semantic version such as `1.0.1`.
- Never ship a production Android build with `version: 'DEBUG'`.
- When incrementing the application version, update both `version` and `version_code`.
- A patch release increments the semantic version appropriately, for example `1.0.0 → 1.0.1`.
- Verify that the Android package/application ID remains unchanged when the intention is an in-place upgrade.
- Never change the package ID as part of a normal update unless creating a deliberately separate application.
- The goal of every normal Android release is for Android to perform an in-place upgrade while preserving application data.

### 7. SQLite Persistence & Data Safety — CRITICAL

- The application's persistent SQLite database is user data and MUST be treated as immutable application state.
- NEVER delete, reset, recreate, replace, truncate, or overwrite the user's persistent SQLite database during feature development, migrations, testing, NativePHP packaging, release preparation, application startup, or application updates.
- NEVER run destructive database commands against the persistent application database, including:
  - `php artisan migrate:fresh`
  - `php artisan migrate:refresh`
  - `php artisan db:wipe`
  - `DROP DATABASE`
  - `DROP TABLE`
  - `TRUNCATE`
  - Equivalent reset/wipe operations
- These commands may ONLY be used when the user explicitly requests a complete database reset and the database being reset is confirmed to be a development/test database.

### 8. Database Migrations

- Every database schema change MUST be implemented using a Laravel migration.
- Apply schema changes with `php artisan migrate`.
- Migrations MUST preserve existing user data by default.
- NEVER solve a migration problem by deleting the database.
- NEVER solve a migration problem by running `migrate:fresh`, `migrate:refresh`, or another reset command against the persistent application database.
- If a schema change requires changing existing data, the migration MUST explicitly transform existing records safely before removing or changing the old structure.
- Prefer additive migrations:
  - Add tables.
  - Add nullable columns.
  - Add columns with safe defaults.
  - Add indexes.
  - Backfill existing records where necessary.
- Avoid destructive schema changes unless they are explicitly required and approved.
- If a migration could cause data loss, STOP and ask the user before implementing or running it.
- Migrations MUST represent one clear schema transition and must not rely on manually deleting or recreating the database.

### 9. SQLite Data Location & NativePHP Updates

- The persistent SQLite database MUST live in the application's persistent writable data location and MUST NOT be treated as a source-code or build artifact.
- NativePHP packaging MUST NOT replace the user's existing writable SQLite database with a database from the packaged application source.
- Do not package a development SQLite database containing local test/user data as a replacement for the user's production database.
- Application updates MUST preserve the existing SQLite database.
- When the updated application starts, pending Laravel migrations may be applied to the existing database.
- The expected update flow is:
  - Existing app.
  - Install updated APK.
  - Preserve existing SQLite database.
  - Run pending migrations.
  - Continue using existing data.
- NEVER implement application startup logic that deletes and recreates the SQLite database when migrations fail.
- If migrations fail during startup, surface/log the migration error and fix the migration rather than destroying the database.

### 10. Development/Test Database Isolation

- Development and test databases MUST be separated from the persistent application database.
- Before running destructive testing commands, verify that the configured database is a disposable development/test database.
- NEVER assume `DB_DATABASE` points to a safe disposable database.
- Do not run database-reset commands merely because a feature requires a clean test state.
- If a clean database is required for automated tests, create/use a dedicated test database.
- Test fixtures and seeders MUST NOT modify the user's persistent application database.

### 11. Seeders & Default Data

- Seeders MUST NOT truncate, reset, or overwrite user-owned data.
- Seeders may create required default/reference records.
- Default/reference data should use safe existence checks or upserts where appropriate.
- Never use a seeder as a substitute for a migration.
- Never automatically run destructive seeders during application startup or production packaging.

### 12. Database Backups

- Before any operation that could potentially modify a large amount of existing user data, create a backup of the persistent SQLite database when practical.
- Do not delete the backup until the operation has been verified.
- For risky migrations or data transformations, recommend or require a backup before proceeding.
- Backups MUST be kept separate from the application's active database path so they cannot accidentally be mistaken for the live database.

### 13. Mobile Layout & Sticky Modal Actions

- All multi-input, long-form, or scrollable mobile modals MUST keep primary actions accessible without requiring the user to scroll to the bottom.
- Use a sticky bottom action footer:
  `sticky bottom-0 z-20 bg-slate-950 px-6 py-4 shadow-2xl`
- Primary actions such as `Save`, `Submit`, and `Cancel` MUST remain visible and usable on small mobile screens.
- Ensure the modal's scrollable content does not hide or overlap the sticky footer.
- Test modal layouts at small Android viewport sizes.

### 14. Authenticated Root Route

- When an authenticated user visits `/`, the application MUST immediately redirect to `/dashboard`.
- Authenticated users MUST NOT see the public landing page or welcome page.
- Unauthenticated users may continue to receive the intended public landing/authentication experience.

### 15. Release Safety Checklist

- Before creating a production Android package:
  - Confirm the application version has been incremented.
  - Confirm `version_code` is greater than the previous release.
  - Run `npm run build`.
  - Confirm `public/build/manifest.json` exists and is current.
  - Confirm `public/hot` is absent.
  - Confirm the persistent SQLite database will NOT be packaged over or replaced.
  - Confirm pending database changes exist as Laravel migrations.
  - Confirm no destructive migration/reset command is being run against the persistent database.
  - Use `--skip-prepare` only when Android/native configuration has not changed.
  - Avoid `--rebuild` unless actually required.
  - Build and sign the Android package.
  - Test the update by installing it over the previous version and verify that existing user data remains intact.

### 16. Agent Safety Rule — HIGHEST PRIORITY

- User data takes priority over build convenience.
- If there is uncertainty about whether an operation will delete, replace, reset, or overwrite the persistent SQLite database, DO NOT perform the operation automatically.
- Stop and ask the user for confirmation.
- Never use database deletion as a shortcut for fixing migrations, packaging problems, dependency problems, startup errors, or development issues.
- Never sacrifice existing user data to make a build succeed.
- When in doubt, preserve the database and investigate the underlying problem.
